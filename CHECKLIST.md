**Region detection (`instance_region`) — hardware + IP, three-signal cross-check, no fabricated content:**
- `jurisdiction.instance_region` (the lookup key for whatever real region-specific ruleset a human has actually loaded — not itself legal content) is auto-filled at config load from real signals when an operator hasn't set one explicitly in `config.toml`; an explicit config value always wins and hardware/IP detection is skipped entirely in that case.
- Three independent real signals, `src/hardware_region.rs`: system timezone (tzdata's own `zone.tab`/`zone1970.tab`, never a hardcoded table), system locale (POSIX `LC_ALL`/`LANG` naming), and IP geolocation (one real HTTP call to ip-api.com's free keyless endpoint, asking only "what country is my own public IP in" — no per-request or per-user data sent).
- Deliberately NOT a locally-bundled IP database (e.g. MaxMind GeoLite2) — that would mean shipping a multi-MB blob that goes stale as IP allocations shift, or needing a MaxMind account this environment doesn't have. A live lookup against a real, currently-accurate service was judged more honest than a bundled table pretending to be current.
- The IP call is short-timeout (3s) and strictly non-fatal — any failure (offline, service down, bad response) yields `None` for that one signal only; boot is never blocked or meaningfully delayed by it, and the other two signals (or an explicit config value) work with zero dependency on it succeeding.
- Agreement rule: `instance_region` is only auto-filled when **at least two of the (up to three) available signals agree** with each other (`HardwareRegionSignals::agreed_region`) — not unanimous-3, not trust-any-1. Rationale: requiring all three would silently degrade coverage the moment any one signal is merely unavailable (e.g. offline); trusting a single signal is exactly the "wrong silent guess" risk this design has rejected from the start. Confirmed live on the actual dev machine: timezone AND IP geolocation both independently resolved to the Dominican Republic while locale resolved to the US — 2-of-3 agree (DO), so `instance_region` correctly auto-fills to `DO` despite the locale outlier.
- `OzoneConfig::load` is now `async` (was sync) purely because of the real IP call — `reqwest::blocking` cannot be constructed from inside an already-running Tokio runtime (`main()` is `#[tokio::main]`) without panicking, so this awaits a real async `reqwest::Client` instead. Single call site (`src/main.rs`) updated; confirmed via `grep` there are no other callers.
- Still, absolutely, no fabricated per-country/state legal CONTENT anywhere — this entire mechanism only improves the accuracy of the lookup *key*, `assets/jurisdiction/` content is untouched by this work.
- Rebuilt, confirmed compiling with zero errors, binary confirmed newer than every touched source file. *Not yet confirmed via a live boot log showing the new 3-signal detection message — pending next server restart.*

Every `/orchestrate` request runs as its own unbounded concurrent task — nothing currently throttles simultaneous orchestrations.

## New findings from the first real openrouter/free live test (2026-09-14)

- **Over-eager clarification-seeking**: a completely unambiguous prompt ("Say hello in exactly one short sentence.") triggered `needs_clarification: true` with 5 clarifying questions (tone? recipient? error-handling branches? language? a verification step?) and `success: false`. A second test with a genuinely ambiguous prompt ("Plan a marketing campaign for our product.") got `needs_clarification: false` structurally (though the model's own generated text asked questions anyway) — confirming this isn't "always triggers," it's inconsistent/model-luck-dependent since free-tier auto-routing picks a different (and differently-calibrated) model per internal call.
  - **Root cause found** (`src/orchestrator/stages.rs`'s `stage_4_zero_shot_simulation`, ~line 706): the simulation prompt asked the model to predict "potential issues or clarifications needed" as one of three required fields per step with zero guidance on the bar for when clarification is actually warranted — any non-empty result unconditionally set `needs_clarification = true` → `success: false`, blocking the whole response.
  - **Fixed**: rewrote the prompt to explicitly require BLOCKING ambiguity only (no reasonable default exists) and explicitly list common non-blocking cases (tone, audience, language, format, error-handling preferences) the model should silently default on instead of asking. **Confirmed live**: both a rebuilt "say hello" retest and a rebuilt SAST-audit retest came back `needs_clarification: false` — verified across multiple retests, no longer model-luck-dependent.

- **CRITICAL bug found: near-universal false-positive container matching, corrupting step context.** The SAST-audit test (`"Write step-by-step guidance for conducting a static application security testing (SAST) audit..."`) took 921.8s and returned complete garbage — a dump of ZSEI's internal modality/category-root tree (`"## ModalityRoot: Modality\nKeywords: modality\n\n## Modality: Text..."` etc.) instead of any real content.
  - **Root cause found**: `KeywordScan::search` (`src/zsei/search.rs:39-72`) — the shared, default search strategy behind `SearchContainersByKeywords`, used by every keyword-based ZSEI container search system-wide — does bidirectional substring matching (`haystack.contains(keyword) || keyword.contains(haystack)`) with **no minimum keyword length**. The query included the single-character word `"a"` (an ordinary word in "...audit on **a** Rust codebase"), and `"a"` is a substring of nearly every keyword in the store (`"modality"`, `"math"`, `"data"`, `"external"`, ...). Every generic structural-root container in the store matched, flooding the step's context with ~25 irrelevant entries that buried the real instruction, and the model (free-tier, and the actual task instruction was positioned LAST after the noise) produced a garbled regurgitation of the context instead of a real answer. 550s of that request's 921.8s total was the single Step Execution call processing this bloated, noise-dominated prompt.
  - **Fixed** (two changes, compounding the same failure mode from different angles):
    1. `src/zsei/search.rs`: `KeywordScan::search` now filters out keywords shorter than 3 characters before matching — they carry effectively no discriminating signal and are the direct cause of the universal-substring problem. Fixes this for every keyword-based container search host-wide, not just this one call site.
    2. `src/orchestrator/stages.rs`'s step-execution prompt template: reordered so "Original request" leads and background context trails, explicitly labeled as optional/ignorable — defense-in-depth so a weak model given legitimately-long context still can't lose track of what it's actually supposed to produce.
  - **Second round found live, after the length-3 fix was already running**: a fresh "Say hello in exactly one short sentence." request still pulled in an entirely unrelated, previously-stored photosynthesis container (`## ModalityGraph: Unknown text graph (29 words...)\nKeywords: photosynthesis, plants, chlorophyll...`) from earlier testing this same session. Root cause: the query keyword `"the"` (an ordinary 3-letter stopword, present in almost any sentence, so it survives a bare length≥3 filter) is itself a substring of **"pho-to-SYNTHE-sis"**. Also found the length filter had only ever been applied to the query side — the haystack (stored container keywords/topics) was never filtered at all, so a short *stored* keyword could symmetrically slip through the same way.
  - **Fixed**: added a real (if non-exhaustive) stopword list (`the`, `and`, `for`, `are`, `this`, `that`, `have`, etc. — ~50 of the highest-frequency English function words) to `src/zsei/search.rs`, filtered on BOTH the query side and the haystack side, alongside the existing length≥3 check.
  - **Also found while investigating**: an existing K-ALGORITHM policy in this codebase is "algorithms are never removed, only superseded — an old implementation gets preserved under its own name as a selectable, non-default option" (not something I introduced — this is how a `/btw` fork correctly resolved a conflict with my first length-3 fix, converting it into `KeywordScan` (new default, id `"scan"`) + `LooseScan` (old pre-fix behavior, preserved and selectable as `"scan-legacy"`) rather than deleting the old behavior outright). The stopword fix applies to the new default (`KeywordScan`) only, per that same policy — `LooseScan` intentionally keeps the original, unfixed behavior available for selection.
  - **K-ALGORITHM search-family wiring note** (see the corrected K-ALGORITHM section below): this `search.rs` logic is the real, live implementation regardless of these fixes — but note `KAlgorithms::global().search`'s own registry instance is disconnected from the real request path (ZSEI's query handler builds its own separate `SearchRegistry::new()`), so switching the default strategy via the K-ALGORITHM facade currently has no live effect; only editing the strategy's own code (as done here) reaches production.
  - **Confirmed live end-to-end after restart**: the same SAST-audit prompt that previously returned a ZSEI category-tree dump now returns a real, correctly-formatted, on-topic answer (`"# Step-by-Step Guidance: Conducting a SAST Audit on a Rust Codebase... ## Phase 1: Tool Selection ### 1.1 Identify Rust-Specific SAST Tools | Tool | Type | Strengths | Best For |..."`) — genuinely relevant content, no leaked calculator/photosynthesis containers, no structural-root dump. Both fixes (this one and the step-prompt reordering) hold up under a real retest.

- **Free-tier latency is real**: 237.9s (~4 min) for a trivial "say hello" prompt even without the above bug. Not a hang — the actual cost of routing every internal call through free-tier OpenRouter models (7 sequential internal LLM calls, 5,685 tokens total for that one request). Worth knowing before mistaking a slow-but-working free-tier response for a stuck one.

- **New CRITICAL bug found: BitNet degenerate token repetition, no anti-repetition sampling configured.** A retest of "Say hello in exactly one short sentence." (after the clarification-overreach fix and search-relevance fix — `needs_clarification` correctly came back `false` this time, confirming that fix works) took 2301s (38+ min) and still returned garbage: `"## Pipeline: Core\nKeywords: core, core, core, core, ..."` repeated dozens of times. Step Execution alone took 1,364,277ms (~22.7 min) and burned ~10,008 tokens — almost entirely the word "core" repeated.
  - **Root cause found**: `execute_bitnet`/`execute_gguf` (`assets/pipelines/general/prompt/main.rs`) invoke `llama-cli` with zero repetition-control flags (no `--repeat-penalty`, no `--repeat-last-n`) — nothing stops this small, heavily quantized (1-bit) local model from looping on a single token once it starts, burning its entire generation budget and wall-clock time on garbage instead of stopping or producing real content.
  - **Fixed**: added `--repeat-penalty 1.1 --repeat-last-n 256` (standard llama.cpp defaults) to both functions' `llama-cli` invocations.
  - Also worth noting: this test ran under heavy CPU contention (4-5 concurrent `llama-cli` processes at once — 2 manual test retests + the methodology meta-loop drafting 2 real gaps back-to-back), which likely made the degenerate repetition worse/slower to hit its token cap, but contention is NOT the root cause of the repetition itself — that's the missing sampling parameter, confirmed by the complete absence of any repeat-penalty flag in the command.
  - **Confirmed live after restart**: retested "say hello" — routed through OpenRouter free this time rather than BitNet (so this specific fix wasn't exercised by that run), but no repetition garbage appeared in either retest. Not yet caught BitNet in the act of a real generation post-fix to directly confirm the repeat-penalty flags themselves stop a degenerate loop — the underlying `llama-cli` flags are confirmed present and correct in the rebuilt binary, but a live BitNet-routed retest is still worth catching opportunistically (e.g. next time free-tier quota is exhausted) rather than manufactured, since forcing it would mean deliberately breaking the API config.

### Pattern investigated: "Blueprint Assignment" stage consistently ~580s — resolved, not a bug
Across two clean retests (hello: 581.7s, SAST: 580.0s — nearly identical despite completely different prompts), the Blueprint Assignment stage alone took ~9.7 minutes both times. Traced `walk_fallback_chain_standalone` (`src/orchestrator/mod.rs:2231`): it tries each fallback candidate exactly once in order, no hidden retry loop — ruled out a retry-storm bug. Most likely real explanation: this session's heavy concurrent LLM load (multiple manual test retests plus the methodology meta-loop firing at the same time) intermittently hits OpenRouter free's hard 20-req/min cap, causing that specific stage's primary call to fail and fall through to the fallback order's first candidate, `bitnet-i2_s` — whose real cost (model load + up to 1000-token generation at BitNet's genuine ~7-9 tok/s) is roughly constant regardless of prompt content, which is exactly why two unrelated prompts landed on nearly the same duration. Not a code defect; just the already-built fallback system doing its job under real infrastructure constraints (rate limit + BitNet's genuine slowness). No fix needed here beyond what's already landed (repeat-penalty, max_tokens cap).
