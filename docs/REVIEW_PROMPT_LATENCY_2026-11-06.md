**REVIEW ONLY — no code was changed for this document.** It replaces the shorter first version. Every cause has: *what it is · evidence (MEASURED = I computed it from the data/ code this pass; READ = read in code; FORK = reported by the optimization review fork, not re-verified; EST = my estimate, labelled) · effect · status · options*. Evidence sources: `model_calls/model_ledger.jsonl` (29.2 MB, 5,872 rows), `model_calls/pipeline_zero_shot_calls.jsonl` (5,071 text-pipeline calls), host logs, live Stage 2 runs, code, the live OpenRouter catalog, `curl` timings. ## 0. Corrections to what I said earlier (so you are not working from my wrong numbers)
1. **The "19–35% success" figures for Stage 2 calls were an OUTAGE, not normal behaviour.** 2,548 of the 3,433 recorded failures are `OZONE_PROMPT_PIPELINE_PATH not set or binary missing`; on 2026-10-26/27/28 and 11-01 EVERY text-pipeline model call failed (100%), then the path bug was fixed. **Since 2026-11-03 (672 calls): paragraph-detect 81% ok, order-validate 97%, section 91%, boundary-validate 100%, modality-detect 100%.** Current Stage 2 reliability is decent; its problem is call COUNT and per-call TOKENS, not failures.
2. **"Prompt server mode" is NOT a big win for remote models** (≈1–2%: measured connect 0.01 s + TLS 0.08–0.13 s vs 10–14 s per call). Its real value is LOCAL models (cold-spawn load 25–40 s per call; a keep-warm server already exists in code but is off) — see cause 12.
3. **"Batch five votes into one call" is not possible via `n`:** none of the 12 free models lists `n` in `supported_parameters`. The real batching levers are different (cause 14, §3).
4. The ledger parse is ≈0.7 s in Python (read 0.3 + parse 0.39), Rust is unmeasured (not built/run); it is more a MEMORY issue than a time issue on this box (cause 25).

## 1. Stage 2 — text normalization (causes 1–7)
**1. K-ALGORITHM "1×1 in order, dual 5× validation" (the design).** Every section/paragraph/sentence/modality event needs an ORDER check (5 consecutive YES) and then a BOUNDARY/CLASS check (5 consecutive YES) — up to 10 calls per event, plus the detect call, and rejected events re-propose. *Evidence:* READ `validate_section_event / validate_paragraph / validate_modality` (text/main.rs ~3280/3555/3817) · MEASURED live run: a 59-character request = 34 calls in 29 min (18 paragraph-detect, 14 validate, 2 section; 7 failed). Since 11-03: 251 detect + 241 validate calls recorded. *Effect:* ≥34 calls ⇒ ideal 6–8 min at 10–14 s each; observed 25–30 min. *Status:* CAPTURED by design (never-skip). A tiny-input fast path is allowed as an OPT-IN knob only — NOT implemented. *Options:* reduce calls per event without skipping: batch DIFFERENT independent questions (cause 14), reuse (cause 6), cheaper per-call tokens (cause 14).
**2. Votes run strictly one after another.** READ `confirm_times_*`. *Effect:* a 5× check = 5 × ~14 s ≈ 70 s. *Status:* ONE vote primitive now (UNCOMPILED): the text pipeline and the host's AMT validation both call `k_validation::confirm_consecutive_with` (previously two separate implementations plus a copy). The "5×" IS a run of yes/no ballots — not two systems; the K-algorithm's "dual 5×" means the two sequential checks per event (order, then boundary). OPT-IN — `[optimization] concurrent_votes` / `profile="high_end"`: first vote gates, remaining 4 run concurrently (same all-5-agree rule); sequential stays default. Compiled and live-run only partly (the test walks used it before it became opt-in); not measured end to end. *Caveat:* concurrency is bounded by the 20 rpm limiter and, with the proven model, the 5 votes are near-duplicates (cause 14).
**3. The two checks of one event run back-to-back.** READ `validate_paragraph`: order 5× then boundary 5×. *Effect:* second check waits for the first. *Status:* CAPTURED (speculative second check: start check-2's first vote while check-1's votes 2–5 run; discard if check-1 fails).
**4. Votes were sent WITHOUT their instruction.** READ `k_validation::yes_no_input` put the "answer with ONE JSON object" text in `system_context`; `PromptInput` has no such key (serde dropped it). MEASURED/READ via a key scan across all prompt-pipeline callers: this was the only live offender. *Effect:* models answered freely (prose / long reasoning); unparseable ⇒ treated as non-affirming ⇒ rejection ⇒ re-propose. The size of the latency gain is UNMEASURED (needs a run). *Status:* FIXED (sent as `system_prompt` and appended to the prompt; unit test fails if a non-PromptInput key is added). Votes stay at temperature 0.0 (operator ruling).
**5. Weak router members vote wrong or junk ⇒ rejection ⇒ re-propose.** *Evidence:* MEASURED ledger — `openrouter/free` 1,245 calls: 610 success, 384 empty, 215 other error, 26 HTTP, 10 timeout (49% success); `nemotron-ultra` 77% over 1,383; today's alternation of detect/validate in `pipeline_zero_shot_calls.jsonl`. NOTE these are ledger rows (host walk calls); the text pipeline's own success since 11-03 is 81–97% (different layer). *Status:* partly FIXED — non-chat members re-called/recorded as failures, proven model tried first inside the `openrouter/free` slot (host chain and prompt binary), chain order unchanged. Failures behind the router still can't be attributed to a member (cause 30).
**6. Identical content is re-analysed every run.** *Evidence:* READ chunk graphs persist with `content_hash = [0u8;32]` (text/main.rs:101) and nothing looks up an existing analysis; MEASURED 24 persisted files contain the same test sentence and 12 another — i.e. analysed and persisted that many times. 5,071 recorded text-pipeline calls, 1.07 M tokens in paragraph-detect alone. *Effect:* every repeat pays full Stage 2 (6–30 min). *Status:* FIXED in code (UNCOMPILED) — **analysis reuse store** in the text pipeline: `<data_dir>/analysis_cache/text/<key>.json`; key = two FNV-1a 64 hashes over (pipeline version `text-analysis-v1`, text, chunk size, depth, entity/topic flags, sorted available modalities, processing path, executor model class, grammar mode); the entry stores the FULL text (a hit needs exact equality — a collision can never return another document's analysis), the window it was analysed under, and the whole `TextModalityOutput`. Failed analyses are never stored. A hit returns with `analysis_reused: <key>` in the output and zero model calls. **Operator ruling applied:** no model tier in the key and NO replacement logic in code — re-running with another model is done as needed (E2E rerun / meta / ripple / file beacon); to force a fresh analysis run with `OZONE_ANALYSIS_REUSE=0` or clear the entry. `OZONE_ANALYSIS_REUSE=0` turns the store off. Bump `ANALYSIS_PIPELINE_VERSION` when the algorithm changes.
**7. Every detect/validate call re-sends the whole chunk.** *Evidence:* READ prompt bodies carry `CHUNK TEXT`; MEASURED detect median 3,219 tokens (p90 7,935), validate 1,228 (p90 4,749). *Effect:* tokens and latency scale with chunk size × events. *Status:* CAPTURED — provider prompt-prefix caching is not exposed on the free models (UNVERIFIED), so the lever is fewer/larger-batched questions, not caching.

## 2. Model layer (causes 8–15)
**8. `openrouter/free` rotates members and ~half its ledger calls fail.** (numbers in cause 5.) *Status:* partly FIXED (above).
**9. Free-pool latency.** MEASURED ledger medians: `walk:pipeline-9` 10.3 s (p90 40.7 s); `openrouter/free` 10.2 s (p90 38.2 s); `nemotron-ultra` 14.3 s (p90 33.5 s); `methodology_compliance_check` 5.4 s; `amt_detail_extraction` 8.6 s; `response_graph_render` 11.2 s. **10. **13. **14. Reasoning models spend ~1,000+ tokens on a one-word answer.** MEASURED: 342 validation calls, median **980 tokens**; since 11-03 order-validate median **1,228** (p90 4,749), boundary-validate 473 — for an answer that needs ~10 tokens. Default `"provider"` = today's behaviour, because the effect on vote accuracy is unmeasured — flip after an A/B. JSON mode (`response_format`, 7/12 members) NOT added (an unsupported member could 400); the instruction fix already asks for JSON. *Options:* none left in code until measured. Whether turning reasoning off lowers vote ACCURACY is unmeasured. *Also:* with the proven model every vote hits ONE member at temperature 0, so 5 votes ≈ 1 vote of information (the router's rotation used to supply variation) — you ruled "it's yes/no, near-identical is fine"; that makes strength-N a pure cost/failure-tolerance knob (`DEFAULT_STRENGTH = 5` is "a parameter, not a law" per the code) — your call whether N should change per member tier.

## 4. Host orchestration (causes 19–24)
**19. Serial independent awaits.** READ/MEASURED: `lane_split.rs` runs lane parts in a `for` loop awaiting each; relation windows (16 modalities) await one window at a time; FORK: provider tools within one step, per-paragraph sentence listing, modality loops, plus the blocking-subprocess-in-async pattern in modalities. *Effect:* wall time = sum, not max. *Status:* CAPTURED (opt-in parallel routes; ordering/merge must stay identical).
**20. Cross-modal link loop.** READ `graphs.rs`: it needs **5 consecutive passes with zero new edges**, safety ceiling 30 passes (`pass > 30`), and each pass executes link pipelines (text↔others, then inter-modality) — so every walk with ≥1 graph pays ≥5 passes even when nothing links. Per-pass cost is UNMEASURED. FORK (not re-verified): the pass counts any `link_result` as new even when nothing was added, so it may never stabilise (it reported every text→3D link failing on an unknown `ReferencesModality` variant). *Status:* CAPTURED.
**21. Methodology rule text re-read from disk.** READ: `load_methodology_rules_full` is called at 5 sites (`amt.rs:3386`, `amt_loop.rs:685`, `stages.rs:891/1645/2107/3311`; the fork said 7). Each reads container + content file. *Effect:* small per call, multiplied by methodologies × steps. *Status:* CAPTURED (cache per walk).
**22. Methodology sufficiency review adds ≥1 call per request.** READ — runs in the DETACHED meta loop (does not block the walk); chunked by the reading model's window ⇒ more calls for many/large methodologies. *Status:* by design; counts against the daily quota.
**23. Watchdog 1,800 s, resume restarts from the beginning.** MEASURED logs: tasks 1049, 1073, 1096, 1097 "walk failed before task creation — recorded as a PAUSED task (resume re-runs the walk from the start)". *Effect:* a slow Stage 2 throws away ≤30 min. *Status:* CAPTURED — stage-level resume (checkpoint after Stage 2) and a Stage 2 budget derived from the call plan.
**24. Admission gate tiers (User > Lane > Loop).** READ `pipeline/gate.rs`: detached loops yield to user work. *Status:* OK by design (can delay meta work under load).

## 5. I/O and storage (causes 25–31)
**25. The prompt binary re-reads the ledger and catalog on every call** (my `proven_free_model()`). MEASURED: ledger **29.2 MB**; **89.7% of the bytes are `prompt` bodies, 6.7% `response`, and the fields the function uses (`model`,`kind`) are 0.93%**; Python read+parse 0.7 s (Rust unmeasured, EST 0.1–0.2 s ⇒ 1–2% of a 10 s call). *Real risk:* memory — each process parses every line into a `serde_json::Value` (holds the 25 MB of prompt strings) — EST 60–150 MB per process × up to 5 concurrent on a box with ~2 GB free; UNMEASURED (not run). *Status:* FIXED in code (UNCOMPILED): the host rewrites a derived `model_calls/model_stats.json` (per-model attempts/outcomes/median latency; temp file + rename; once at first load and after every recorded row) and the prompt binary reads THAT (~10 KB) — falling back to the ledger only if the file is absent. `OZONE_PROVEN_FIRST=0` still disables the rule.
**26. Every prompt call is a new process** (spawn + config load + TLS). MEASURED: connect 0.01 s, TLS handshake 0.08–0.13 s, total 0.32–0.38 s to `/models` ⇒ overhead ≈0.1–0.2 s per call = **1–2% of a 10–14 s call**. READ: the CONNECT model exists (a pipeline can run `--serve --register`, host dispatches to a registered remote first) — but nested modality callers spawn the binary directly (`SubprocessExecutor`). *Status:* CAPTURED, LOW value for remote models; relevant for local keep-warm (cause 12).
**27. Whole-file JSON rewrites.** READ: gaps/reviews/health/proposals/candidates are read-modify-write of the whole file, unlocked. MEASURED sizes today are small: `amt_reexpansion_candidates.json` 176 KB, `methodology_gaps.json` 17 KB, `capability_gaps.json` 3 KB. *Effect:* negligible now; grows with the no-cap doctrine; and a lost-update race (no lock) is a CORRECTNESS risk under parallel meta routes. *Status:* CAPTURED (append-only + compaction; locks).
**28. Per-edge fetch+rewrite on tool-output graphs.** READ (before the edit): one `get_container` + one `UpdateContainer` per edge; degree² container rewrites. *Status:* FIXED in code (per-source batches, no size refusal) — UNCOMPILED.
**29. Chat history scan.** READ: `recent_chat_context` reads every turn file each call; MEASURED only 13 turn files exist today (negligible); sizing by model budget edited. *Status:* FIXED partly (uncompiled); the directory scan remains for large histories.
**30. Ledger corruption — CORRECTED: historical, the writer is already fixed.** MEASURED: 63 of 5,872 lines unparseable (truncated JSON + blank lines), ALL at line ≤4302 (rows dated up to ~2026-10-26); none after. READ `model_ledger.rs`: rows are appended in ONE `write_all` (O_APPEND) and the loader salvages interleaved objects ("tolerant recovery"). So there is nothing to fix in the writer; what remains is (a) a one-time repair/compaction of the old lines and (b) failures behind the router still carry no served model (unattributable) and (c) the 29 MB size (prompt bodies). *Status:* writer FIXED earlier; (a)(b)(c) CAPTURED.
**31. Observability gaps hide the delays.** FORK/READ: nested prompt-binary stderr (limiter waits, router re-calls, proven-model fallbacks) is discarded on success; many loop call sites record latency 0. *Status:* host log persistence FIXED (uncompiled until restart on the new build); stderr capture + call-site latency CAPTURED.
