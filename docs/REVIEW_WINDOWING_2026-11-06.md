## 2. Findings (captured; edit only where ledger says so)
- **W1 (CORRECTED — operator: the two windows are different on purpose).** The doctrine is MODEL-AGNOSTIC: no fixed limits anywhere; every stage works by the size of the model that will READ the call, and a model switch re-derives everything from the new size. Where this lives (read from code/docs): `resolve_context_limit` (orchestrator/mod.rs:1104) — order is explicit: (1) a requested id's OWN registered window, "the global [models] value is never consulted for it"; (2) no id → the ACTIVE backend's window (`[models].context_length` = 128,000 for the router default); (3) unknown id → the registered OpenRouter entry; (4) last resort active. So registered `openrouter/free` = 32,000 (that entry's own window, used when it is the requested model) and 128,000 (the active-backend default) are two intended values for two roles, not a conflict. `resolve_processing_path` (mod.rs:1828): context ≤ 8,192 ⇒ **Path2** (granular loops, constrained SLMs) else **Path1** (whole-chunk deconstruction); `build_amt_layer_by_layer` (chunk path, many small calls) vs `build_amt_from_graphs` (richer context, fewer calls) are "two views of the same process" serving model-size tiers (TOP_DOWN_REVIEW_GUIDE §9/§10: *"Smaller models loop more; that is truth, not degradation… the full context is always delivered — in portions the model can handle"*). Stage 2 passes `max_chunk_tokens = model_context_limit/4` (floor 256) so chunking scales with the model; the text crate's `default_max_chunk_tokens()` = 2000 is only the standalone default when a caller passes nothing. CONTEXT_BUDGET_SERVICE §2.4/§4 still says "fixed 2000 tokens (today)" — **stale vs code** (orchestrate path is already model-sized); update the doc, no code change.
- **W2 (CORRECTED).** The host-loop default for an UNKNOWN window (8,192, conservative) vs the text pipeline's "unknown ⇒ keep the chunk whole and flag `window_unknown`" are two policies in two places. Under the model-size doctrine the open question is only: when the size is genuinely unknown, which is safer — captured, undecided, no edit.
- **W3 (SHARPENED 2026-11-06 with evidence) The prompt binary never chunks or cuts, and only branch-discovery lanes chunk per candidate.** Ledger shows the blueprint-assignment prompt (76 KB) and a clock step prompt (163 KB) reaching a 4,092-token BitNet unchanged; `lane_split` (per-candidate re-render + halving + ordered merge) is the right mechanism but is wired to AMT branch lanes only. Universal fix = chunkable calls (sections + merge rule) re-rendered per candidate window — NOT a skip-by-size guard (tried, reverted). Original note: `context_truncated` is a flag nothing consumes. Over-window ⇒ provider error ⇒ generic "unusable" retry (same call). A call that is over-window will fail identically on retry. → a pre-call guard (host or binary): if estimate > window ⇒ do not retry the same call; chunk (caller) or pick a larger-window candidate.
- **W4 Loops TRIM where text CHUNKS.** `context_budget::assemble` cuts (recorded) — used by meta draft, assistant digest, I-Loop, AMT prompts. Text normalization, relation windows, decision review, network dialogue chunk instead. "Chunk where we can": candidates in loops = assistant/I-Loop signal sets (window the signals, merge), AMT branch generation (≈608 calls) context, meta draft keywords/topics (small).
- **W5 Relation windows are count-based, not token-based** (30 nodes/window). With node content now kept whole (the 80-char cut was removed) a window of 30 long nodes can exceed a small window. → token-aware windowing (`windows_by_tokens(items, budget)`) using the reading model's window.
- **W6 ~75 prompt-side `.take(N)` lists + 63 `chars().take(N)` still cut model input** (REVIEW_ALIGNMENT "nothing dropped" list). The honest fix is per-site windowing (W5 pattern), NOT deletion: the binary does not chunk (W3), so deleting a cap turns a silent cut into an over-window failure on small windows.
- **W7 Traversal/span-out seeds** were `take(40)` + a 12-keyword floor — a hidden cut in front of a budgeted best-first walk. Removed (ledger E7); the walk's own token budget and `fetch_cap` guard bound the work.
- **W8 Votes (`confirm_times`) and 5× checks** use `fit_chunk_to_window(.., reserve 20, ..)` — consistent with W1/W2 caveats; the chunk itself (≤ window/4) is what is validated.
- **W9 Proven-in-slot** (nemotron-ultra, 1M window) is safe w.r.t. windows sized for 32k/128k (conservative); the router fallback is where W1 bites.
- **W10 Stage 2 cost is not window-related** (K-algorithm 1×1, dual 5× — see REVIEW_OPTIMIZATION): a 59-char request is one chunk.
- **W11 Single oversize item.** One methodology/node larger than a whole window cannot be chunked further without splitting its text; `assemble` trims it (recorded). Needs a text-splitting policy for single huge items (split on structure, carry state) — not built.

2. **A provider step was planned for a rule whose condition did not apply** (a test methodology's rule declaring `threed-mcp` for a "zzsuff … added case" was attached to a text explanation). Methodology rules are not evaluated against the request before a provider step is inserted for them (partly test-induced, but the mechanism is real). CAPTURED, not fixed.
**L28 (edited, uncompiled):** new in-walk step between Stage 6 and Stage 7 (`close_capability_gaps`, `draft_methodology_for_capability`, wiring in the walk sequence in `stages.rs`):
1. **JUDGE** each still-unjudged missing capability: *"Can the request be fully and correctly completed WITHOUT it?"* — strength-5 consecutive YES (`confirm_yes_no_orch`); unanimity is required for the risky action, DROPPING a requirement. Dropped → status `not_needed` (reason + `resolutions` history kept in `capability_gaps.json` via new `tool_binding::set_gap_status`) and removed from `state.missing_capabilities`.
2. **CLOSE** every gap still judged necessary: draft ONE real methodology on the spot (grounded in the registered providers/tools; placeholders rejected; rules declare `requires` providers so a truly missing provider is still recorded as wanted) and persist it through pipeline 12 `Create`; status `methodology_drafted`; the new id joins `state.methodologies`.
