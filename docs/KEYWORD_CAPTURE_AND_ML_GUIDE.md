Operator rulings that shape this document (2026-11-08, verbatim intent): **not rarity-first** ("no point in most-rare-first"); **hits are tracked and feed our ML**; the **zero-shot expansion is left to the END** (it identifies the true keywords that remain, validates what are hits, then the scoring function runs); **no false confidence** (no model-reported scores — judgments are yes/no via the strength-N loop, scores are counts/ranks of observed evidence); **stopwords may be TESTED as a baseline but are never relied on again**; token-aware matching "maybe"; **language-neutral filler handling belongs to the ML/embedding**, which should be a **real custom production model trained on real data** (not a mock/dev one); decide **tool/MCP vs pipeline** from the guides; and identify **everything that must be captured, per container type, at every point** where keyword search is used.

## 2. Doctrine applied
1. **No false confidence.** Nothing the model self-reports is a score. A keyword is *validated* (yes/no, strength-N, drops need unanimity) or not. Ranking uses **counts of observed events and structural facts**, output as an **ordinal rank**, never a probability or a "confidence"; UI shows Verified yes/no only. `TraversalMLModel.confidence_threshold` is therefore **retired from the design** — a model is promoted by a **yes/no held-out evaluation** (§7), not a threshold.
2. **Zero-shot expansion last.** Capture everything deterministic first; the model then expands and judges; hits validate over time (§5).
3. **No fixed caps; the window/budget decides.** Ranking exists so the budget keeps the best, not so results are cut.
4. **Stopwords: test, don't rely.** Three lists exist today — `zsei/search.rs` `STOPWORDS`, `request_terms.rs` `STOPWORDS`, and the substring/length heuristic. Per the policy "algorithms become selectable options, never dropped", they stay registered as a **baseline strategy**; the evaluation harness (§8) measures them against the learned filler handling; none is the default dependency.
5. **Rarity-first is withdrawn.** (My 2026-11-08 proposal "rank by IDF" is superseded by the operator ruling; document frequency may still be a *feature* the learned ranker is free to use or ignore, never the ordering rule.)
6. **Ozone-first taxonomy** (`TOOLS_PIPELINES_MCP_GUIDE.md` §1): *pipelines* are Ozone's own computation, shipped and versioned with it; *tools/MCPs* are external capabilities Ozone consumes/exposes. The ML (§6.4) is placed accordingly.

## 3. HITS — what to track, where, and how (so it can train the model and score)
A **hit** = a (query term → container) match event produced by a search. Event kinds, in order of strength: `returned` (search matched) → `seeded` (became a seed) → `packed` (made it into a step context / span-out window) → `kept` (a strength-N yes/no judgment affirmed it: methodology relevance E13, rule applicability E14, capability necessity) / `dropped` (unanimous judgment against) → `applied` (a methodology id actually carried by a blueprint step; a container the step's accepted output depended on) → `human` (a decision-review resolution or UI "Verified" yes/no).
**Storage — two layers (so reads never storm the single write path):**
1. **Append-only event log** `zsei_data/keyword_hits.jsonl` (same pattern as `walk_metrics.jsonl`): one line per event `{ts_ms, trace_id, call_site, query_terms[], term, container_id, container_type, match_class, event, scope{project,workspace}, step?}`. Cheap, never blocks a read, IS the training data.
2. **Rollup into the container** by a periodic meta-loop pass through the ONE write path (one batched write, one ripple): `hints.access_frequency` (= count of `returned` since creation), `hints.last_accessed`, `hints.hotness_score` **derived from real use** (replaces the invented 0.5–0.9 literals — see FABRICATED_OUTPUT_AUDIT X2), and per-term hit counters in a new sidecar (§4) — not by rewriting the container on every search (that would ripple on every read).
**Call-site capture points** (the ~28 in §1.4): the search door itself (`zsei/query.rs` SearchContainersByKeywords) logs `returned`; span-out logs `packed`; the E13/E14/closure judgments log `kept/dropped`; blueprint/AMT consumption logs `applied`; decision_review logs `human`.

## 5. The keyword SETTLEMENT pass — zero-shot expansion at the end
Runs **after** the container exists and its graph is built, **off the walk's critical path** (a ripple-triggered meta-loop actor like the AMT/meta/I loops — Stage 2 is already the slowest stage), incremental per container, chunked to the reading model's window (no cap):
- **Pass A — verbatim capture** (deterministic, no model): everything in §4 marked verbatim/identifier/name.
- **Pass B — expansion (Z)**: one batched call per window returns synonyms / related terms / aliases / likely request phrasings / translations, in the content's language(s). Adds only; unanimity not required.
- **Pass C — keeper judgment**: for each questionable extracted term, a strength-N yes/no "is this a true content-bearing keyword for this container?"; **a term is removed only on unanimous NO** (assured drop). Fixes garbage (`you`, whole sentences) at the source instead of hiding it at search time. Each judgment is logged as a labelled sample (§7).
- **Pass D — hit validation over time**: the rollup (§3) makes counts real; terms that never hit, or are repeatedly `dropped`, are *re-judged* by Pass C (never silently deleted by a counter).
Query side: the request's keywords go through the same A→B→C once per request (E16 re-ask generalised), cached with the request graph.

## 6. SCORING (the function) and the custom ML
### 6.1 The scoring function — deterministic v0 (no model confidence)
A match's **rank key** is an ordered tuple of observed facts, compared lexicographically (no weights invented by hand): (1) in-scope yes/no; (2) match class — exact name/identifier > exact keyword > whole-token > substring (substring is a last class, not a gate); (3) number of distinct query terms matched; (4) validated yes/no on the matched term; (5) the matched container's real hit history (`applied` > `kept` > `packed` > `returned` counts); (6) graph hops from the request graph (nearer first); (7) recency of `last_accessed`. Ties keep store order. Output = an ordinal position; the span-out/step budget truncates. This replaces the flat 0.5.
### 6.2 What a learned model adds
Weights and interactions the tuple cannot express, and **language-neutral filler handling**: terms that never predict a kept/applied container get a low learned contribution automatically — the ML-native replacement for a stoplist, in any language.
### 6.3 Can we build a REAL custom ML now, on real data? — honest answer
**Yes, in two stages; not as a single from-scratch embedding model today.**
* **Data reality:** the store has ~2.5k content-bearing containers locally (Derived 1,689 are mostly run markers; real content = ModalityGraph 314, Methodology 290, Experience 285, JurisdictionRuleSet 159, FileReference 156, Blueprint 45, ChatTurn 18…), 3,366 distinct terms, 3,713 relationships (PartOf 1,127, Follows 969, ForkOf 723, RelatedTo 666, SimilarTo 205), **zero recorded hits and no retained judgment labels** (the `strength_n_vote` ledger rows I read carry no prompt/answer, and the stage logs record only kept/dropped COUNTS). That is too little text to learn a language-capable embedding from scratch, and no hit labels exist **yet**.
* **Stage 1 — build now (runs on this hardware, no new dependency): a keyword/term ranker + a hashed character-n-gram term↔container encoder (fastText-style), trained contrastively on Ozone's own graph and its hit log.** Char n-grams make it language-neutral, typo/inflection-robust and able to handle unseen words; ~2^16 buckets × 64 dims ≈ 16 MB; trains in minutes on 4 CPU cores; inference microseconds in pure Rust. Positives = (term, container) pairs from validated keywords, verbatim-evidence-accepted relations (`semantic_relations` accepted vs rejected sets), strength-N `kept` vs `dropped` judgments, `applied` methodologies, human decision-review rows; negatives = sampled non-matches and `dropped` pairs. The ranker (logistic/GBDT-style over the §6.1 facts + encoder similarity) is trained on the same log. **It cannot be trained until the hit/judgment log (§3, §7) has collected real labelled events — Phase 0 is capture.**
* **Stage 2 — when real data justifies it:** fine-tune a small pretrained sentence encoder (384-dim, matching `embedding_dimension = 384`, e.g. a multilingual MiniLM-class model; **a third-party weight download — an operator decision**) on the pairs above, CPU offline (hours), served as ONNX/native inference; fills `context.embedding` and enables a true `use_ml` semantic mode. Requires adding an inference runtime (a dependency decision). Not needed for v1.
### 6.4 Placement — tool/MCP or pipeline? (guide-based)
Per `TOOLS_PIPELINES_MCP_GUIDE.md` §1 and the ozone-first test: **the model is Ozone's own computation, intrinsic to search/traversal (the slots live in the core container schema, §16 of the spec) → PIPELINES**, not an MCP: (a) **inference** = a pipeline (own crate, `{data, context}` envelope, runs in-process fast path; the host search calls it via the registry gate); this also **replaces the stub `TraversalML` (#17)** rather than adding a parallel unit; (b) **training** = the same crate in a `train` mode, an offline job that reads the real graph **only through `/zsei/query` (gated, metered)** and the hit log, writes a versioned model artifact; (c) the **model artifact is a graph citizen**: a `TraversalMLModel` container (model_file, version, trained_on_samples, **held-out accuracy/precision/recall measured, never self-reported**, status), registered like `detection_models/registry.json`. **An MCP/tool is only warranted for an external heavy trainer** (e.g. a Python fine-tuner for Stage 2) — that would follow `NEW_MCP_GUIDE.md` Pattern A and its §6 checklist verbatim: security model first (it must read data via the gate, never the disk), locked-by-default, a TESTED refusal path, platform+version tags, registration with live-derived tool list, called only via `/mcp/call`, one ledger row + one ripple verified, persistent-process launch story, contract container in ZSEI. Not needed for Stage 1.

## 7. Training data and the promotion rule (no false confidence)
Labelled-sample sources, all real: `keyword_hits.jsonl` events (§3); **every strength-N judgment recorded as a labelled sample** (request/container text refs, question, YES/NO, N, model, trace) — today only counts are logged, so **this logging is the first edit**; validator accepted/rejected relation sets; `applied` methodology ids; decision-review human resolutions; UI "Verified" yes/no. **Promotion:** a trained model becomes `Active` only if, on a **held-out split of real hits it has never seen**, it **beats the deterministic v0 tuple on the same split** (yes/no) with the metric (precision@budget, recall of `applied`) *measured and stored*; otherwise it stays `Inactive`/`Validating`. A demoted model never silently serves. No fabricated metrics anywhere (house rule).

## 8. Evaluation harness (real system, no mocks)
Golden requests against the real store: for each, the containers that were `applied`/`kept` (from the log) are the relevant set; measure **precision@budget, recall, out-of-scope rate, hits-per-term, substring-vs-exact inflation** for: (a) default scan (baseline), (b) token-aware, (c) v0 tuple, (d) stoplist variants (the "test stopwords" baseline the operator allowed), (e) learned. Track in the walk scorecard next to the stage metrics. The decoy-project test (`span-walk.mjs` SW1b/1c/7) is the scope-leak member of this harness.

THIRD WAVE — persistence, hotness read for ranking, literal removal (edited 2026-11-08; operator: "why are keyword hits being archived when they should be persistent no matter size … lift that instruction and update them … hotness read for ranking … remove the confidence ones now, capturing what is removed first … edge weight you decide … then build and test")
1. **Hit log persistence — rotation REVERSED.** The size-based rotation/archiving added in §12 is removed: nothing in the host rotates, archives or truncates `keyword_hits.jsonl` or `judgment_samples.jsonl`; they are the training data and persist no matter how large they grow. Size is handled by streaming instead: the **rollup reads from a byte offset in slices of ≤ 64 MiB** (a host-memory guard on how much is in memory at once, not a cap on what is consumed; the loop continues until the whole log is folded) and **aggregates events per container** `(kind, query terms) → (count, newest ts)` so a search that returned thousands of ids costs one small entry per id; the **dataset builder streams** the log line by line in two passes (labels, then time-ordered facts) and never holds it in memory. `hit_log_files()` still reads any `keyword_hits.archive.*.jsonl` an operator moves aside by hand. (My §12 line "Hit-log rotation DONE" is superseded.)
2. **Hotness is read for ranking.** `RankFacts.hotness` = packed ÷ returned from the rolled-up real counts (0.0 when never returned); it is in the deterministic v0 key (after the ¬dropped fact, before the raw packed/returned counts) and a feature of the learned ranker (`FACT_FEATURES` 13 → 14; an old saved ranker fails the length check and is simply not used until retrained). The ranking recomputes it from `keyword_meta["*"]` — it never trusts a stored `hints.hotness_score`.
3. **Invented literals removed, after capturing them.** 239 node `hotness_score:` + 295 graded edge `weight:` + 11 graded `confidence:` literals replaced in production code (hotness → 0.0 = no observed use, edge weight → 1.0 = present, confidence → 0.0 = not affirmed); `zero_shot_simulation` no longer asks the model for a confidence (its verdict is the yes/no `feasible`); the biology filter reads observed hotness (`> 0.0`). The manifest of every removed literal (file, HEAD line, old/new value, reason, source line) is `docs/evidence/literal-removals/2026-11-08-removed-literals.jsonl`; the full account is `docs/LITERAL_REMOVAL_2026-11-08.md`.
4. **Edge weights — my decision, from what the system has:** structural presence is 1.0 (kept); the invented gradings are gone; the REAL signal is now captured: every `packed` event carries its relation label and the rollup accumulates `edge_use_stats.json` (`{relation: windows filled through it}`). The expansion priors in `span_out.rs` (`relation_weight`) stay as class priors for expansion ORDER (they carry no edge-confidence term); switching them to the observed order is a later, data-backed step.
5. **Known limits:** old graph files/containers keep their old invented values until re-analysed; `RankFacts` is serialized with the new `hotness` field (`serde(default)`, so old datasets still load).
